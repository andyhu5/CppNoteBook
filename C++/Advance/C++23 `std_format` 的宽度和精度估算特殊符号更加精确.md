

## 问题的根源：C++20 的宽度估算从哪里来

`std::format` 的宽度和精度说明符（`{:10s}`、`{:.5s}`）在处理字符串时，需要知道每个字符在终端上占多少列——这个数字通常是 1，但东亚全角字符（汉字、日文假名、全宽标点等）占 2 列。C++20 引入这个特性时（P1868R1），宽度估算规则用的是一份硬编码的码点范围列表，来自 Markus Kuhn 写的 `wcwidth` 的 Unicode 实现。

这份列表在当时是合理的出发点，但它有两个结构性问题，随着时间推移会越来越严重。

**第一个问题：不准确。** 列表里有些码点被分类为宽度 2，但实际上它们的 Unicode `East_Asian_Width` 属性并非 `Wide` 或 `Fullwidth`，只是在特定历史实现中被顺带包含进去了。LWG 3780 给出了具体的反例：

```
U+3248..U+324F（圆圈数字，如 ㉈ ㉉）
   C++20 规定宽度为 2，实际 East_Asian_Width 属性是 Ambiguous，
   并非明确的宽字符，改为宽度 1 更符合 Unicode 规范。

U+231A WATCH（⌚）、U+23E9 BLACK RIGHT-POINTING DOUBLE TRIANGLE（⏩）等
   C++20 规定宽度为 1，但它们实际上是宽字符（East_Asian_Width = Wide），
   应该是宽度 2。
```

这直接导致 `std::format("{:^6}", "⌚")` 产生的对齐结果，在实际终端里是错的——格式库以为 ⌚ 占 1 列，填充了 5 个空格，但终端渲染 ⌚ 时实际占 2 列，对齐偏移一个字符。

**第二个问题：不具备前向兼容性。** C++20 的规范是一份固定的码点列表，而 Unicode 标准每年发布新版本，持续增加新字符。C++20 列表在 Unicode 14 发布时就已经没有更新，到 Unicode 15/15.1 时进一步落后。列表里还包含了大量当时尚未分配的码点（"reserved"），这些位置将来可能被分配给完全不同的字符，届时规范就彻底错乱了。

## P2675 的修复：改用 Unicode 属性驱动的规则

原本的规范基于从 `wcwidth` 实现衍生的码点范围，P2675 把宽度估算规则改为直接依照 Unicode 的 `East_Asian_Width` 属性定义：宽度为 2 的字符，是 `East_Asian_Width` 属性值为 `Fullwidth (F)` 或 `Wide (W)` 的码点，其余所有码点宽度为 1。

这个变化看起来简单，但在语义层面是质的跳跃：

```
C++20 规则：宽度 2 = 某份硬编码列表里的码点
C++23 规则：宽度 2 = East_Asian_Width 属性为 Wide 或 Fullwidth 的码点
```

后者是一个算法定义，而不是一个静态列表。实现可以直接从最新版 Unicode 数据文件（`EastAsianWidth.txt`）生成对应的查找表，每次 Unicode 版本升级，只需更新数据文件并重新生成，规则本身不变。这就是"前向兼容"的含义——标准规范不会因 Unicode 新版本而过时。

## 另一个修复：扩展字形簇（extended grapheme clusters）

P2675 同时修正了另一处：对于 Unicode 编码的字符串，宽度估算应当基于扩展字形簇（extended grapheme clusters）的首个码点，而不是对每个码点单独计算。

这处改动针对的是组合字符序列。一个用户可见的字符（如带重音的字母 Á）有时由多个码点组成：基字符 `A`（U+0041）加上组合重音符 `◌́`（U+0301）。如果按码点逐个计算宽度，这个字符会被计为 2 列宽；按扩展字形簇计算，它只是一个用户可见字符，宽度为 1。

libstdc++ 在 GCC 14 里为此引入了完整的 Unicode 15.1.0 字形簇分割规则（`GraphemeBreakProperty.txt` 和 `emoji-data.txt` 的完整实现，新增约 4700 行代码），从而做到对任意 Unicode 字符串给出正确的列宽估算。

## 对代码的实际影响

这个变更会改变部分字符的格式化输出，属于行为变更而非纯 bug 修复，但委员会认为从不正确的行为变成正确的行为是可以接受的。可以用 feature-test macro 检测实现是否已应用此规则：

```cpp
#include <format>
#include <string>

// ⌚ (U+231A WATCH) 在 C++20 下宽度估算为 1，
// 在 C++23 P2675 修复后宽度估算为 2（East_Asian_Width = Wide）
auto s = std::format("{:^6}", "⌚");

// C++20 实现（错误）："  ⌚   "  — 以为 ⌚ 占 1 列，填了 5 个空格
// C++23 修复后（正确）：" ⌚  "  — 知道 ⌚ 占 2 列，填了 4 个空格
// 在等宽终端里，后者才能真正居中对齐

#ifdef __cpp_lib_format
    // __cpp_lib_format >= 202311L 表示 P2675 已应用
#endif
```

核心结论是：这个修复把 `std::format` 的宽度估算从一个"凑合用的静态近似"改成了一个"基于 Unicode 标准属性的、可随 Unicode 版本演进的正式规则"。对于只处理 ASCII 的代码没有任何影响；对于处理东亚字符、emoji 或组合字符序列的代码，格式化对齐的结果会更准确。
