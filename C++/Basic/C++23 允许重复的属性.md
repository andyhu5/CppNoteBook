# C++23：DR — 允许重复的属性（Allow Duplicate Attributes，P2156R1）

## 背景问题：C++ 属性（Attribute）语法的历史限制

C++11 引入了标准化的**属性（attribute）**语法，用 `[[...]]` 来给声明、语句等附加元信息，比如：

```cpp
[[nodiscard]] int compute();
[[deprecated]] void old_function();
[[maybe_unused]] int x;
```

C++ 标准里对属性列表的语法一直有一条隐含（且在不同标准版本里表述不完全一致）的限制：**同一个属性在同一个属性列表（同一对 `[[...]]`，或者跨多个相邻的 `[[...]]` 组合）中不能重复出现**，即使这个属性本身是无参数的、重复写两遍在语义上完全没有歧义或冲突。

```cpp
[[noreturn, noreturn]] void fatal_error(); // C++23 之前：可能被拒绝，报重复属性错误
```

## 问题场景：为什么会"意外"产生重复属性

这个限制在**手写代码**里很少主动踩到（没有人会故意写两遍同一个属性），但在**宏展开、模板生成代码、代码生成工具**等场景下，重复属性是很容易"意外"产生的：

### 场景 1：宏组合导致属性重复

```cpp
#define ALWAYS_INLINE [[gnu::always_inline]]
#define HOT_PATH [[gnu::always_inline]] [[gnu::hot]]

ALWAYS_INLINE HOT_PATH void critical_function(); 
// 展开后：[[gnu::always_inline]] [[gnu::always_inline]] [[gnu::hot]] void critical_function();
// C++23 之前：可能因为 gnu::always_inline 出现了两次而报错
```

### 场景 2：模板/泛型代码里，某个属性可能通过不同路径被附加到同一个声明上

比如某些用宏或模板参数控制是否添加 `[[nodiscard]]` 之类的代码生成模式，在某些参数组合下可能意外重复展开出同一个属性。

### 场景 3：多个第三方宏/库各自独立地给同一个声明附加了语义相同的属性

当多个宏定义（可能来自不同的头文件、不同的库）各自"好心"地给某个函数加上同一个属性（比如都加了 `[[nodiscard]]`），组合在一起使用时就会触发重复属性的编译错误，而这原本不该是使用者需要操心的事情。

## C++23 的修正：允许重复属性，语义上等价于只写一次

C++23（P2156R1，作为 DR 追溯生效）明确规定：**同一个属性在同一属性列表中重复出现是合法的**，其效果等价于只写一次：

```cpp
[[noreturn, noreturn]] void fatal_error();  // C++23 起：合法，等价于 [[noreturn]]

[[nodiscard]] [[nodiscard]] int compute();  // C++23 起：合法，等价于单个 [[nodiscard]]
```

这个修正**不仅适用于标准属性**（如 `nodiscard`、`deprecated`、`maybe_unused`、`noreturn` 等），也适用于**带命名空间的实现相关属性**（如 `[[gnu::always_inline]]`、`[[msvc::...]]` 等），只要它们语义上是"无参数或参数完全相同的重复标记"。

## 一个细节：带参数的属性重复时如何处理

对于**带参数**的属性（如 `[[deprecated("reason")]]`），如果重复出现且参数不同，标准仍然要求这属于错误或未指定行为（因为参数不同意味着语义上产生了冲突，无法简单地"合并成一个"）。C++23 主要解决的是**无参数属性**、或**参数完全相同**情况下的重复问题，允许编译器直接"去重"处理。

## 为什么归类为 DR（缺陷修复）

这项改动同样被认定为对 C++11 以来属性语法设计的一个**实用性缺陷修复**：标准委员会认为"因为宏展开、代码生成等常见工程实践导致的属性重复，不应该被视为程序员的错误而拒绝编译"，这属于语言易用性上的一个明显疏漏，值得直接修正规则本身。因此各编译器厂商也倾向于**追溯性地**在更早的标准模式下就采纳这个宽松规则（很多编译器实际上早就以扩展形式支持了这一点，C++23 只是把这种"事实上的宽容"正式纳入标准）。

## 实际影响

- 对**直接手写属性**的代码几乎没有影响；
- 主要受益的是**大量使用宏来组合/条件化附加属性**的代码库（尤其是需要跨平台、用宏抽象不同编译器的属性语法的项目，比如封装 `ALWAYS_INLINE`、`NODISCARD` 之类的可移植宏时），减少了因为宏组合意外产生"重复属性编译错误"的维护负担；
- 库/框架的用户在混用多个第三方宏、或者模板代码自动生成属性时，不再需要小心翼翼地担心"两个库都给同一个函数加了 `[[nodiscard]]`会不会冲突"。

## 小结

这是一项典型的"消除因工程实践（宏、代码生成）产生的、本不该视为错误的边界情况"的语言易用性修正——把"同一属性在同一声明上重复出现"从**潜在的编译错误**，明确为**合法且语义等价于只写一次**，从而让基于宏的属性组合、代码生成工具等常见的 C++ 工程实践更加健壮，不再因为属性的意外重复而中断编译。这也延续了本轮讨论的一系列 C++23 DR 修正的共同主题：**让标准规则更贴合实际工程需求，消除历史遗留的、不必要的严格限制**。
